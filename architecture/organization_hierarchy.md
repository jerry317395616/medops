# 组织层级与版本

## 范围

COD-018 在唯一自研 App `medops` 的 `HRP Organization` 模块内实现医院组织主数据、
版本化层级和生效日期查询。它不修改 Frappe、ERPNext、Frappe HR，也不在本任务中建立
`Department` 或 `Cost Center` 映射。

## 聚合模型

| DocType | 作用 | 生命周期 |
| --- | --- | --- |
| `HRP Hospital` | 稳定医院边界，关联 ERPNext `Company` | 可修订，已有版本后法人不可变 |
| `HRP Organization Version` | 某医院完整组织树的生效日期版本 | 服务创建，草稿可维护，发布后不可变 |
| `HRP Organization Unit` | 版本内 Nested Set 节点 | 只能随草稿层级整体替换 |

医院编码和节点编码使用大写 ASCII、数字、下划线或连字符。节点名称支持中文。一个版本
最多 2000 个节点且序列化载荷不得超过 2 MB，必须恰好包含一个允许下级的医院根节点，
根编码必须等于医院编码。无论客户端提交 JSON 字符串还是已解析数组，都执行同一载荷限制。

## 版本规则

1. 创建版本时锁定医院记录，分配医院内单调版本号。
2. 同一医院同一生效日期只允许一个版本。
3. 层级替换要求当前 `revision`，整树校验通过后才删除旧草稿节点并写入新节点。
4. 相同摘要为无操作，不增加修订号；旧修订号返回 `IONE-CORE-0005`。
5. 发布时重新读取并验证完整树和摘要，然后提交版本。
6. 已发布版本、组织节点和发布时间不能修改、取消或删除。
7. 按日期查询选择 `effective_from <= effective_on` 的最新已发布版本。

## 服务与 API

| API | 方法 | 语义 |
| --- | --- | --- |
| `CORE-009` | POST | 创建或按修订号更新医院 |
| `CORE-010` | POST | 创建草稿组织版本 |
| `CORE-011` | POST | 原子替换草稿版本的完整组织树 |
| `CORE-012` | POST | 发布并冻结组织版本 |
| `CORE-013` | GET | 按版本或医院与日期查询组织层级 |

四个写 API 都必须提供 `Idempotency-Key`，由共享 `DomainService` 在同一事务内保存加密
响应。层级替换的幂等请求只包含版本、期望修订号、节点数和摘要，避免持久化组织名称与
备注。服务不调用 `frappe.db.commit()`。

医院创建先校验权限与公司，再解析幂等重放；医院存在性与期望修订号在领域写入阶段校验。
因此成功的首次创建可以安全重放，陈旧修订仍会回滚幂等预留并返回冲突。

## 权限与审计

- `System Manager`
- `HRP System Manager`
- `HRP Data Steward`

医院允许上述角色通过标准表单维护，并使用修订号避免并发覆盖。组织版本和组织节点在
Desk 中只读，写入必须经过领域服务。审计仅记录版本号、修订号、节点数、变化字段和
层级摘要。

## 系统设置迁移

`HRP System Settings.default_hospital` 从 Data 升级为 `HRP Hospital` Link。已有文本在
首次 migrate 时按 `Company + 旧标识` 生成确定性 `LEGACY-*` 医院记录，文本保留为医院
名称。迁移可重复执行；若旧标识与现有医院法人冲突则失败关闭，防止静默串法人。

## 运维与回滚

升级前执行完整数据库备份，再通过 Press 使用锁定上游 Bench 运行 migrate。迁移后检查
三个新 DocType、复合唯一约束、系统设置 Link 和 Error Log。

回滚应用代码并 migrate 时保留新表和医院记录。COD-017 会继续把医院编码作为受控文本
读取，因此不需要删除或反向转换生产数据。已发布版本只能保留或由后续版本替代。
