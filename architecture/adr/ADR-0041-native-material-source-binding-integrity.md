# ADR-0041 原生采购申请的预占来源完整性

## 背景与问题

预占根保留独立授权及来源快照，完整历史读取仍须核对当前原生采购来源。锁定的 ERPNext `372dff2` 中，采购申请停止/重开经 `StatusUpdater.set_status` 调用 `Document.db_set`，不经过普通保存钩子。采购行的 `db_set` 同样可能改变已绑定金额。Frappe `4880ad1` 原生重命名还会直接更新 Dynamic Link，可能改写不可变根的来源标识。根的原生链接能阻止正常取消/删除，但不足以保护停止、经济编辑或忽略链接的内部调用。

## 决策驱动因素

保留标准控制器与既有权限；有预占事实的来源保持可核验；允许正常采购进度与未绑定行操作；不能因关闭财务入口而失去历史保护。不把拒绝保护冒充取消、修订、承诺或实际使用闭环。

## 备选方案

1. 修改上游控制器或数据库触发器：拒绝。
2. 只在普通保存/取消时检查：不足以覆盖原生 `db_set` 和改名。
3. 在 MedOps 使用标准 DocEvents，按实际绑定行比较受保护事实并拒绝破坏性转换：采用。

## 决策

在 Material Request 的 `before_save`、`before_update_after_submit`、`before_change` 检查已登记来源；`before_cancel`、`on_trash`、`before_rename` 拒绝处理已有根引用的原记录。Material Request Item 的 `before_change` 保护已绑定行，`on_trash`、`before_rename` 拒绝删除或改名该行。原生改名会在自身权限校验前调用钩子，故改名钩子先显式核验原生写权限，再查询私有绑定。

钩子先取得当前采购父行锁，再用当前锁定读取查询该父单的全部根绑定，不能使用普通 REPEATABLE READ 旧快照证明没有预占。已有预算围栏时只可重访其预先绑定父单，泛预算围栏或未绑定父单在取得迟到锁之前拒绝并使围栏失效。子行先发现父单，按父单→子行顺序重读并比较父属；发现移动或删除则冲突，不能用旧父属放过已绑定子行。每父单最多读取10000根，超出拒绝；此为安全拒绝界限，不是医院容量证明。

有根的父单必须保持已提交采购申请及现有完整历史支持的进度状态；法人、日期、类型、父标识不变。按登记行标识逐项比较物料、单位、成本中心、费用科目、项目、数量、单价和金额；绑定行不得消失、复制或改名。修改时间、备注和受支持采购进度不作为经济变更；未绑定行保留原生操作。十进制从 MariaDB 文本读取，原生内存浮点只用于与原精确值比较，舍入或丢位不能被当作相同，不能用于财务授权或金额运算。

无根记录时继续原生业务行为；无根的旧确认在来源变更后仍由原决定/快照协议拒绝。保护不依赖人工操作总开关或私有写开关，不授予新角色、范围或链接分享，也不创建财务事实。钩子无提交、无原生源写入、无外部调用；失败由原生外层请求完整回滚，死锁/锁超时转换为冲突，不局部重试。安装/迁移阶段且根表尚不存在时不阻止初始化；正常运行缺少根表则配置错误。

## 后果

已被引用的原采购记录不能通过通用停止、取消、删除或改名来破坏核验，即使相关预占已经释放。后续取消/修订需单独定义原生业务状态与不可变财务历史兼容、关闭未结额和重新授权的协议；此决策不授权忽略引用或自动释放。分摊承诺、实际转换、组织/映射等其他来源依赖、所有直接 SQL/`frappe.db.set_value` 入口和全局并发顺序仍须独立实现或审查，不能据此宣布全部写入口已闭环。

## 验证与退出条件

纯逻辑验证进度/未绑定行、受保护字段、丢行/复制、精确值与浮点丢位、终态拒绝。原生临时绑定表测试真实采购保存、状态方法、子行 `db_set`、原生改名、直接生命周期钩子及共同围栏顺序；该临时行只是绑定存在性，不证明合法财务授权。专用已提交 CI 以完整真实根/历史及 Cookie 请求验证原生停止/改价/取消拒绝，原生采购进度可继续，原根和事实不变，后续完整查看/恢复仍通过。需要当前源码完整普通/Core CI、权限矩阵、真实 Desk、性能和医院验收，不能自动生产启用。

## 迁移与回滚

无新 DocType、列、索引、角色或财务模型迁移；正常升级需刷新钩子/站点缓存并重载 Python 进程，维护期间不访问服务器。存在合法绑定后，不能仅关闭预占开关就移除保护；回退应保留等效来源保护，或先把受影响采购原生入口置于维护状态，直至替代协议就绪。保留全部原始/续期/释放证据、根、事件和加密回执，不改写财务字段来通过兼容检查。

## 安全与合规

拒绝信息不含私有绑定、金额、理由或凭证，不新增公共写 API。当前原生控制器继续承担其已有认证、权限和事务；保护只减少破坏性变化，不替代其业务规则或财务授权。所有 Frappe 生态依赖继续使用用户锁定 fork，不修改上游。
