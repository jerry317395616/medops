# ADR-0035 重叠预算期间的共同事务围栏

## 背景与问题

ADR-0034 以实际起止日期标识期间，但不同且重叠的日期范围产生不同锁。若两笔事务各锁自己的期间、再检查是否存在重叠，仍可能并发通过检查。会计年度也可能存在交叠，不能把年度差异当作天然隔离。原型尚未部署或连接财务业务。

## 决策驱动因素

同一预算池内不同期间需要共同事务边界；同键与跨期写入安全、确定性锁序、独立组织并行、标准 Frappe/MariaDB 复用，以及医院规模下可测量的竞争。

## 备选方案

1. 仅锁具体日期区间：不同重叠区间互不阻塞，拒绝。
2. 对每一天分别建立锁：可减少不相交日期间的等待，但年期预算可能产生数百次锁写入，增加成本和实现复杂度。
3. 同时锁完整期间和去除年度/日期的共同预算维度：保守串行同一预算池的期间，选择此方案，待真实负载评估后可再替换。

## 决策

延续 ADR-0034 对实际日期、来源真实名称、币种精度和事务边界的要求。每个规范键生成两种锁：`v3:period` 绑定完整键；`v3:scope` 绑定公司、医院、原始组织、预算分类、资金来源和项目，故同一范围内不同年度、重叠或不重叠期间都先后执行。两种名称均只含固定前缀和摘要，最长不超过锁定 Frappe `tabSeries.name` 的100字符。批量最多1000个预算键、最多2000个锁名，去重并对所有锁名统一排序，再以参数化原子写入和 `SELECT ... FOR UPDATE` 获取 InnoDB 行锁，持有到事务结束。锁不存金额、不授予权限。

此共同锁只提供互斥，不决定不同期间是否可以共用额度。事务入口须预先收集完整键集合并一次性获取所有锁，不得在持锁后按不确定顺序增补；原型本身尚未强制此事务级规则。启用业务写入之前，服务须先解析实际来源名称并获得所有相关共同锁，然后在相同事务完整检查重叠区间、额度事件和当前授权；业务规则未明确时应拒绝不相同的重叠期间。所有下达、冲销、调整、预占、释放、承诺及实际写入必须共同遵循围栏，禁止旧 v1/v2 或不持锁的混版写入。死锁必须交外层整笔重试，不能在领域服务中提交或重启事务。

## 后果

不相交期间也会在同一预算范围内串行，是明确的保守代价；不同组织或预算范围仍可并行。该设计不能代替医院业务策略、成本中心或跨组织共享池定义；可能影响热点科室吞吐，须按目标规模压测。锁行只含摘要和非财务计数，不新增模型、迁移或角色。旧原型没有生产写入，正式启用时需停止全部旧 worker 和旧写入口。

## 验证与退出条件

测试同范围跨年及重叠期间共有锁、不同组织隔离、多键锁顺序；真实 MariaDB 跨进程验证同范围等待、不同范围并行、回滚释放及无遗留测试行。业务服务还需验证重叠期间失败关闭或正确共享额度、100并发不超额、来源别名、权限撤销、全批回滚和下达冲销竞争。当前实现未接入业务写入且数据库测试尚在等待，不能据此认定并发安全或生产容量。

## 迁移与回滚

当前原型未部署，不迁移现有预算。未来启用后须先停所有新旧财务写入口及 worker、保留并核对事务与事件，再切换或回退；不得让旧前缀或无围栏代码处理新额度事实，不得删除财务证据。

## 安全与合规

内部锁不是 API 或授权。后续仍须当前角色、范围、原生字段与来源权限、职责分离、幂等和脱敏审计；医院业务与生产验收另行完成。
