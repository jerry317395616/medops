# ADR-0022 使用真实单据字段和角色的声明式默认拒绝职责分离

## 背景与问题

本决策延续原 PR #36 的职责分离方案，适配 MedOps 命名空间并纳入尚未提交的运行时引用校验修复。ADR-0021 已用于项目更名，故本方案登记为 ADR-0022。

医院付款、采购、主数据和审批流程要求制单、复核、批准、付款和记账由不同责任人承担。仅依赖角色
名称不能识别同一用户在具体单据上承担了多个职责；允许业务模块自行实现又会产生规则漂移、越权和
不可审计的例外。

## 决策驱动因素

- 必须使用真实单据上下文，调用方不能伪造法人、组织、日期或历史责任人；
- 规则必须可版本化、确定性、可审计且不能执行用户代码；
- 校验不能赋予 DocPerm、数据范围或工作流权限；
- 漏配、损坏配置和规则数量失控必须默认拒绝；
- 响应和日志不能泄露用户、组织、患者或付款单据标识。

## 备选方案

1. 仅使用 Frappe 角色互斥：实施简单，但无法判断具体单据的制单人或复核人。
2. 在每个 Workflow 条件中编写 Python 表达式：灵活，但分散、难审计且引入动态代码执行面。
3. 建立通用动作历史表并记录所有业务操作：能力完整，但本阶段业务流程尚未全部上线，容易形成第二套
   工作流和重复事实源。
4. 使用受控规则声明目标动作、真实单据 User 字段和冲突角色，由统一服务在动作前校验。

## 决策

采用方案 4。规则中的动作和字段均使用封闭白名单；字段必须是标准责任人字段或指向 `User` 的 Link。
服务从真实单据派生组织和日期，先验证调用方读权限、被校验用户 DocPerm 与组织范围，再汇总全部适用
规则。每次请求都重新校验字段、角色和组织引用；任一冲突、无适用规则或引用漂移均拒绝。`CORE-003`
是只读实时查询，不通过幂等快照重放授权决策。只有规则写入 `CORE-032` 通过幂等领域服务和乐观修订完成，
直接 DocType 写入禁止。

`decision_digest` 绑定主体与单据上下文、脱敏决策，以及全部已评估规则的 `rule name` / `revision` /
`policy_digest`，不仅是产生冲突的规则。因此任一适用策略修订都能在不泄露身份原值的前提下改变审计摘要。

## 后果

各领域可复用同一决策，不再复制 maker-checker 逻辑；新增业务 DocType 必须提供明确组织字段和 User
责任人字段。动作执行方必须显式检查 `allowed`，本服务不替代 Workflow。尚未形成的通用动作历史由
后续业务任务按实际单据字段或不可变领域台账补充，不在本任务伪造。

## 验证与退出条件

- 运行 DocType、蓝图、字段目录、API 目录和 OpenAPI 一致；
- 纯测试覆盖白名单、确定性、漏配、责任人和角色冲突；
- Frappe 测试覆盖规则写入幂等、修订锁、实时决策不重放、运行时引用漂移拒绝、权限、组织范围、真实单据、
  直接写保护和 HTTP；
- 任意 SQL、Python、表达式、未知字段、Guest 或缺少规则均无法获得允许决策。

## 迁移与回滚

迁移只新增规则表、索引和工作区入口，不修改现有业务数据。部署前完整备份 Site。回滚应用提交时保留
规则表，不执行删除；重新升级后继续使用。紧急停用必须通过受控修订并保留审计证据。

## 安全与合规

系统管理员维护和执行校验，HRP Auditor 只读。审计只记录 DocType、动作、数量与摘要；响应不返回
用户名、组织值、责任人值或目标单据名。授权决策不持久化重放，规则引用漂移按配置错误默认拒绝。策略不允许动态代码和脚本例外。
