# ADR-0036 预算事务见证与提交回调顺序

## 背景与问题

预算锁在保存点前后可能被撤销，但 Frappe 的保存点回滚不执行事务回调。仅凭连接上的 Python 标记不能证明旧锁仍然有效。锁定 Frappe 的 `Database.commit` 在运行提交前回调之前清除回滚回调；`CallbackManager.run` 按其内部 deque 依次移出回调。若见证过早删除，后续回调失败后错误重试提交可能绕过检查。

## 决策驱动因素

必须失败关闭、保持业务事务原子性、支持原生提交回滚、避免修改上游代码或留下每笔交易的永久见证，明确框架版本耦合及运行边界。

## 备选方案

1. 仅使用连接标记：无法识别回滚到取锁前的保存点，拒绝。
2. 独立会话锁或 Redis：生命周期与数据库事务不一致，拒绝。
3. 使用 InnoDB 事务见证并在提交前末尾复验：采用候选方案，须验证锁定 Frappe 回调实现。

## 决策

预算锁候选在同一事务的 InnoDB `tabSeries` 写入不含业务数据的随机见证，显式检查与正常 Frappe 提交前检查均验证其存在；成功提交前在同一事务删除。回滚至取锁前保存点应撤销见证并使检查失败，正常完整回滚清理连接标记。

候选依赖锁定版本 `CallbackManager._functions` 为 `collections.deque`：取得锁时将见证处理器放在队首，以便在任何普通回调运行前恢复回滚清理；处理器检查见证并将自身移至队尾，直到其他回调及其新增回调执行完，再次检查并删除见证。内部结构不匹配时拒绝取锁。处理器自身失败后重新登记，不能因直接重试正常提交而跳过。此内部依赖必须在 Frappe 升级前重新评审，不修改上游代码。

## 后果

每个受控事务增加一条随机见证的插入、验证及删除。回调队列的内部实现成为锁定版本依赖；不兼容时拒绝取锁而非降级。见证只证明候选事务状态，不证明权限、来源完整或余额。

## 验证与退出条件

事务见证、保存点、早晚回调失败、动态回调、重复提交、连接中断、真实并发和升级兼容均需隔离数据库与 GitHub 集成验证。当前候选未接入财务写入或医院生产。直接 SQL 提交、嵌套提交、手动修改框架回调队列、绕过锁检查或未纳入同一协议的旧写入均不受保护；任何提交异常必须由外层完整回滚。

## 迁移与回滚

见证行仅包含随机标识；正常提交前在事务内删除，回滚由数据库撤销。回退前停止全部使用该协议的写入与工作进程并核对未完成事务，不能混用旧无见证实现或删除财务事实。

## 安全与合规

内部见证不授予 API、角色或财务写权限，不记录预算维度、金额及患者信息；当前角色、字段、组织范围和完整来源仍须在事务内重新校验。
