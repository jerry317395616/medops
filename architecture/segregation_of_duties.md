# 不相容职责校验

## 目标

`HRP Segregation Rule` 为真实业务单据定义声明式职责分离策略。`CORE-003` 在动作发生前校验指定
系统用户是否与单据既有责任人或冲突角色重合，只返回决策与脱敏冲突证据，不提交、批准、付款、
记账或修改目标单据。

## 数据模型

- 规则锁定目标 DocType、受控动作、法人、医院和可选组织单元；身份字段创建后不可修改；
- `actor_fields_json` 最多包含 16 个字段，只允许标准 `owner`、`modified_by` 或目标 DocType 中
  明确指向 `User` 的 Link 字段；
- `conflicting_roles_json` 最多包含 16 个现有角色，用于阻止申请角色兼任审核、审批、付款等职责；
- 至少配置一种冲突来源；有效期、启用状态、修订号和策略摘要受服务管理；
- 所有适用规则同时生效，不以优先级覆盖或弱化另一条硬控制。

受控动作是封闭白名单：`create`、`review`、`approve`、`submit`、`cancel`、`amend`、`post`、
`pay`、`release`、`reconcile`。规则不接受任意动作、字段表达式、SQL、Python、Server Script、
正则或动态导入。

## 校验规则

1. API 调用方必须是 `System Manager` 或 `HRP System Manager`；被校验用户必须是启用的 System User；
2. 调用方必须具有目标单据读权限，被校验用户必须具有动作对应的 DocPerm 和 COD-024 组织范围；
3. 法人、医院、组织单元和业务日期全部从真实单据派生，请求不能覆盖；
4. 仅加载同一 DocType、动作、法人、医院、日期和组织范围内的启用规则，最多 100 条；每次校验都重新确认
   责任人字段仍是指向 `User` 的 Link，角色和组织引用仍有效，引用漂移按 `CONFIGURATION_INVALID`
   默认拒绝；
5. 任一规则发现用户等于责任人字段值或拥有冲突角色，即返回 `allowed=false`；
6. 没有适用规则时默认拒绝，返回 `NO_APPLICABLE_RULE`，防止通过漏配绕过硬控制；
7. 响应只包含发生冲突的规则名/编码、修订、策略摘要、匹配字段名和角色名，不返回用户、
   组织或责任人原值；
8. `decision_digest` 绑定决策上下文与全部已评估规则的 `rule name` / `revision` / `policy_digest`，
   包括没有命中冲突的规则；任一适用规则的身份、修订或策略改变都会改变摘要；
9. 每个 `CORE-003` 请求都从当前单据、用户角色、权限、组织范围和规则实时重新决策。它不接受也不创建
   幂等快照，`idempotency_replayed` 仅为统一响应字段且恒为 `false`；服务仅产生脱敏审计事件，不写目标
   单据、职责冲突业务表或 `HRP Service Idempotency`。

付款制单与审批分离可配置为：目标动作 `approve`，责任人字段 `owner`、`reviewed_by`，冲突角色
`HRP Applicant`。调用方仍须在实际 Workflow 或领域服务执行动作前检查 `allowed`；本任务不替代
Frappe Workflow。

## API 与 Desk

- `CORE-003`：实时、只读校验不相容职责，不要求 `Idempotency-Key` 且不重放旧决策；
- `CORE-032`：管理员幂等创建或修订规则；
- `CORE-033`：管理员和审计员只读查询规则定义；
- “权限与授权”工作区提供“职责分离规则”入口。

规则只能通过领域服务写入。DocType 直接插入、修改、重命名和删除均拒绝。读权限限系统管理员和
HRP 审计员；审计员不可写。

## 迁移与回滚

迁移新增一张规则表和两个复合索引，并同步“权限与授权”工作区。部署前必须完整备份数据库、公开
文件、私有文件和站点配置。回滚应用提交时保留规则数据，不执行破坏性删除；旧版本不会消费这些
记录。紧急停用某项控制应先完成风险批准，再通过幂等修订停用规则。

## 验证

纯测试覆盖白名单、边界、绑定全量适用策略的确定性摘要、责任人/角色冲突和漏配默认拒绝。Frappe
集成测试覆盖元数据、索引、工作区、直接写保护、规则写入幂等、乐观锁、实时决策不重放、运行时引用漂移默认拒绝、
真实单据上下文、DocPerm、组织范围、HTTP 与 Guest 边界。
